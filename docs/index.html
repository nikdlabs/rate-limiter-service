Two strategies, one interface

Sliding Window vs. Token Bucket

Both implement the same RateLimitAlgorithm interface — Spring auto-wires a Map<String, RateLimitAlgorithm> keyed by name, so a rule picks its algorithm with a single lookup, no branching anywhere in the codebase.

Sliding Window Counter
strict

Blends the current window's count with the previous window's, weighted by elapsed time — closing the boundary-burst gap a naive fixed-window counter leaves open. Best for login attempts, OTP requests.

estimated = prev × (1 − elapsed/window) + current
Token Bucket
burst-friendly

Each user holds a bucket of tokens that refill continuously, computed lazily on read — no background job. Idle users can burst on return. Better UX for general API traffic.

refillRate = limit / windowSeconds (per second)
